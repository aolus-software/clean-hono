# Rule: Internationalisation (`src/libs/i18n/`)

Every user-facing string this API returns — response messages, error messages, mail subjects,
validation messages — is a **catalog key**, not an English literal. The i18n layer is hand-rolled and
lives entirely in `src/libs/i18n/`.

## The two entry points

```ts
import { t } from "@i18n";

t("profile.retrieved");
t("role.nameExistsFor", { name });
```

- `t(key, vars?)` resolves against the **current request locale**. Use it everywhere inside a request.
- `translate(key, vars?, locale?)` takes an explicit locale. Use it only where there is no request
  locale — a BullMQ worker, a seed script, a startup log line.

`key` is typed `TranslationKey`, so a typo or an unregistered key is a **compile error**.

## Catalogs: two flat files, moved together

- `src/libs/i18n/locales/en.json` and `src/libs/i18n/locales/id.json`.
- Both are **flat** maps of dotted key to string (`"auth.invalidCredentials"`). The dots are part of
  the key.
- `DEFAULT_LOCALE` is `en` (`src/libs/i18n/types.ts`), the fallback for an unsupported locale and for
  a key missing from a supported one.
- Interpolation is double-brace: `"Welcome, {{name}}"`, filled from `vars`.

**`en` and `id` move together.** A key added to one is added to the other in the same change.

## `keys.generated.ts` is generated

`src/libs/i18n/locales/keys.generated.ts` declares the `TranslationKey` union and is written by
`src/libs/i18n/scripts/generate-keys.ts`. **Never hand-edit it.** After touching either catalog run
`bun run i18n:keys` and commit the regenerated file with the catalog change.

## Where the locale comes from

`localeMiddleware` (`src/libs/hono/middlewares/core/locale.middleware.ts`, global in `src/app.ts`)
reads `Accept-Language`, resolves it with `parseAcceptLanguage`, stores it with `enterLocale`, and
sets `Content-Language`. `getCurrentLocale()` reads it back from an `AsyncLocalStorage`.

Producers handing work to a queue capture `getCurrentLocale()` and pass it in the job payload
(`lang`), because the async store does not survive the hop into the worker.

## Validation messages

`translateZodIssue(issue)` (`src/libs/i18n/validation.ts`) maps a Zod issue onto the `validation.*`
keys. When you add a constraint it cannot classify, add both the key and the branch — do not let raw
Zod English through.

## Don't

1. Don't write an English literal into a `ResponseToolkit` message, a thrown `@errors` class, or a
   mail subject. Use a key.
2. Don't hand-edit `keys.generated.ts`.
3. Don't add a key to `en.json` only.
4. Don't translate log messages — logs are read by operators.
5. Don't translate internal detail: database error codes, constraint names, field names in a structured
   error payload.
6. No `t()` in a repository. A message belongs to whoever throws, which is the service.
